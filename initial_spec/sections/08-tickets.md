## 8. Tickets

### 8.1 Store

One markdown file per ticket, in repo-relative column folders:

```text
/app-name-1/tickets/backlog/
/app-name-1/tickets/open/
/app-name-1/tickets/in-progress/
/app-name-1/tickets/blocked/
/app-name-1/tickets/done/
/app-name-1/tickets/closed/
/app-name-1/tickets/closed-wont-do/
```

`/app-name-1/` is repo-relative. Do not use GitHub Issues unless the user later says to. Comments live in the ticket file body.

### 8.2 Shared increment, typed prefix

One increment across all types.

- `F-07-DB` — database
- `F-08-DM-BL` — data model + business layer
- `F-09-CTL-UI-JS` — controllers, UI, JavaScript
- `TA-13` — technical architecture for DesignArchitect-warm (§8.13)

`F` and `TA` share the increment.

### 8.3 Ticket files and column folders

Column = folder. Filename is identity only: `F-10-DB.md` or `TA-13.md`. Do **not** put state in the filename.

Moving a ticket = move the file between folders and update the state field inside the file. Mismatch is a defect.

Filename parts: kind prefix `F` or `TA`; shared increment; type abbreviations for `F-` tickets; `.md`.

Example: `/app-name-1/tickets/open/F-10-DB.md`.

### 8.4 Board states

The column formerly called `todo` is named **`open`**.

| Token / folder | Who may move *into* this folder | Cap |
|---|---|---|
| `backlog` | **Only** KanbanMaster-cold (from design spec, during ceremony) | any |
| `open` | **Only** KanbanMaster-cold via `backlog → open` | **10** |
| `in-progress` | Worker-cold when they start the approved ticket | typically 1 |
| `blocked` | Worker-cold or KanbanMaster-cold | any |
| `done` | Worker-cold or human after test (or gut-skip accept) | any |
| `closed` | **Only** KanbanMaster-cold, `done → closed` | any |
| `closed-wont-do` | KanbanMaster-cold or human | any |

`done` is not terminal. Do not collapse `done` into `closed`.

### 8.5 Human-readable title

Lives inside the file. Not required in the filename.

### 8.6 Discovery comments

Workers write: extra skills; extra living-knowledge files loaded; extra work discovered; stop-rule events (§5.7); each friction event (`friction += 1` plus a concise comment).

Comments addressed to the Kanban master must say so.

### 8.7 Why column folders exist

Listing `/tickets/<column>/` is the cheap board index. Titles, friction, depends-on stay in the ticket file. `kanban.md` is generated (§8.10).

### 8.8 Kanban ceremony (cannot be skipped)

A ceremony is a fresh KanbanMaster-cold instance. New `backlog` tickets come from reading the design spec. If `backlog` and `open` run dry, work stops until a ceremony runs.

When filling `open`, cluster related tickets so the same Worker-cold can be reused (§5.11).

The Kanban master also reviews `in-progress` / `blocked` / `done` / comments / friction; presents blocker options or escalates; writes TA tickets for design gaps (problem only); closes accepted `done` tickets; regenerates `kanban.md`; does not edit the design spec.

### 8.9 Friction counter

Integer field on the ticket, default 0, no cap. Not a 1–5 opinion score. Worker increments by 1 per fail event and leaves one concise comment. Shown on the kanban row. Kanban master looks at it; does not compile it into files.

### 8.10 Kanban board file (generated)

Path: `/app-name-1/kanban.md`. Human does not hand-maintain it. Source of truth = ticket files (folder = state). Generated by the agent that last moved or edited a ticket. Worker-cold shows this board first on spawn.

Rows: ticket code, title, folder/state, friction, created-by.

### 8.11 Extra work mid-ticket (no worker-created tickets)

Workers do **not** create tickets. Comment on the current ticket → human spawns KanbanMaster-cold → that agent creates the new ticket. Do not shrink a design-level coupling problem into a cute ticket.

### 8.12 Ticket body fields

`Created by`, `DateTimeCreated`, `TicketType` (unabbreviated), `friction` (int, default 0), `Depends on`, state matching the folder, human title, comments log.

### 8.13 TA tickets

Prefix `TA`, same increment, same folders. Example: `/app-name-1/tickets/open/TA-13.md`.

Only KanbanMaster-cold creates them. Worker never does. Content is the problem, impact, needs — self-contained, no recommended design solution. DesignArchitect-warm must not follow a non-TA dependency unless the TA is incomplete. Design architect marks TA `done` with a concise solution comment; Kanban master closes it after any spec change is already written.
